# Нативный HTTP-контракт внешнего RAG (Tier 1) — полный референс

Это руководство — для тех, кто реализует контракт платформы **напрямую** (свой
FastAPI/Flask/Express/что угодно эндпоинт), а не через `causa-rag-client`.
Если ваш RAG на Python и вы не против добавить зависимость — см. сначала
[connector-guide.md](connector-guide.md): `serve()` оборачивает пару функций
в этот же контракт за вас, и большая часть этого файла вам не понадобится.

Этот гайд нужен, если:
- ваш RAG не на Python (контракт — обычный JSON поверх HTTP, языконезависимый);
- вы уже своя HTTP-обвязка (FastAPI-приложение и т.п.) и хотите просто добавить
  два эндпоинта в неё напрямую;
- вы (человек или агент) хардните/дорабатываете уже существующую интеграцию
  и вам нужен точный реестр полей контракта, а не только happy-path пример.

Типичная форма такой прямой интеграции — FastAPI-приложение с собственным
LangGraph-пайплайном, выставляющее `/platform/query` и `/platform/retrieve`
поверх уже существующей внутренней логики. Примеры кода ниже основаны на
реальной, уже прошедшей хардненинг интеграции такого вида.

## Два эндпоинта

Платформа вызывает ровно два URL — оба вы указываете при регистрации:

| Эндпоинт | Метод | Что делает |
|---|---|---|
| `url` (полный, обязателен) | `POST` | Retrieval + генерация ответа |
| `retrieve_endpoint` (опционален) | `POST` | Только retrieval, без LLM-вызова (быстрее и дешевле для чисто retrieval-метрик) |

Если `retrieve_endpoint` не задан, платформа сама паде back на полный `url` и
просто отбрасывает текст ответа — так что можно начать с одного эндпоинта, а
`retrieve_endpoint` добавить позже как оптимизацию.

## Request — что присылает платформа

```json
{
  "query": "Какой штраф предусмотрен за просрочку поставки?",
  "top_k": 5,
  "filters": {},
  "trace_id": "407b8318-d2f0-4196-83ff-4a44c0c4cd75",
  "corpus_id": "handbook",
  "pipeline_id": null,
  "reranker_id": null,
  "params": {"prompt_version": "v2"}
}
```

| Поле | Тип | Обязательно ли читать | Смысл |
|---|---|---|---|
| `query` | `str` | да | Текст вопроса |
| `top_k` | `int` | да | Сколько источников вернуть |
| `filters` | `dict` | нет | Произвольные фильтры — можно игнорировать, если не поддерживаете |
| `trace_id` | `str` | нет, но полезно | Сквозной id для логов — прокидывайте его в свои логи/трейсы, чтобы связать запрос платформы с записью в вашем Langfuse/логах |
| `corpus_id` | `str \| null` | **да, если у вас больше одной коллекции/индекса** | Какой корпус/коллекцию вашего векторного стора обслуживать — см. раздел ниже, это частая забытая деталь |
| `pipeline_id` / `reranker_id` | `str \| null` | нет | Актуально только для `services/reference_rag_server` платформы (дог-фудинг встроенных стратегий); сторонний RAG просто игнорирует |
| `params` | `dict` | нет | Расширяемые произвольные knobs (temperature, версия промпта и т.п.) — читайте только ключи, которые сами объявили в `supported_params` при регистрации |

## corpus_id — самая частая упущенная деталь

**Если ваш сервис обслуживает больше одного корпуса/коллекции, `corpus_id` —
это единственный канал, которым платформа сообщает, какую коллекцию
запрашивать.** Поле объявить недостаточно — его нужно реально прочитать и
использовать при выборе коллекции.

Найдено вживую: в одной интеграции поле `corpus_id` было объявлено в модели
запроса, но нигде не читалось («tolerated, not interpreted») — векторный стор
создавался один раз при старте с единственной жёстко заданной коллекцией.
В результате прогон с любым `corpus_id` молча отвечал из одной и той же
коллекции — не ошибка, а тихий не-эффект, который выглядит как "плохой
recall", а не как баг маршрутизации.

Плохо (то, что было найдено):

```python
class PlatformRequest(BaseModel):
    corpus_id: str | None = None  # объявлено, но нигде не используется

@router.post("/query")
async def platform_query(body: PlatformRequest, ...):
    # vector_store всегда с ОДНОЙ жёстко заданной коллекцией из настроек
    results = vector_store.dense_search(embedding, top_k=body.top_k)
    ...
```

Хорошо — резолвить коллекцию по `corpus_id` на каждый запрос (или кэшировать
per-corpus_id клиент, если пересоздание дорого):

```python
_collection_cache: dict[str, VectorStoreService] = {}

def _resolve_collection(corpus_id: str | None) -> VectorStoreService:
    name = corpus_id or settings.qdrant_collection  # None -> дефолтная коллекция
    if name not in _collection_cache:
        _collection_cache[name] = VectorStoreService(
            url=settings.qdrant_url, collection=name, dim=embedding_service.dim,
        )
    return _collection_cache[name]

@router.post("/query")
async def platform_query(body: PlatformRequest, ...):
    vector_store = _resolve_collection(body.corpus_id)
    results = vector_store.dense_search(embedding, top_k=body.top_k)
    ...
```

Если у вас всего один корпус — можно честно игнорировать поле, но тогда
проверьте, что датасет/прогон на платформе тоже настроен без `corpus_id`
(или на дефолтный), иначе будет то же самое тихое несоответствие.

## Как узнать, каким эмбеддером(-ами) проиндексирован корпус

Найдено вживую: `corpus_id` резолвился в правильную коллекцию, но запрос всё
равно падал с ошибкой векторной БД о несовпадении размерности — RAG считал
эмбеддинг запроса СВОЕЙ моделью (768-мерной), а корпус был проиндексирован
платформенным BGE-M3 (1024-мерным). Название коллекции — не гарантия того,
каким эмбеддером она заполнена.

`GET /corpus/collections?realm_id=<realm_id>` (тот же эндпоинт, что отдаёт
список корпусов для выбора `corpus_id`) возвращает и это — каждая запись
несёт `backends`, где у каждого физического хранилища может быть свой
`embedder_id`:

```json
[
  {
    "realm_id": "demo",
    "corpus_id": "handbook",
    "backends": {
      "qdrant": {"collection": "demo__handbook__structure_aware__bge_m3", "embedder_id": "bge_m3"},
      "opensearch": {"index": "rag__demo__handbook__structure_aware"}
    }
  }
]
```

`embedder_id` — на уровне конкретного бэкенда, не одно поле на весь корпус:
корпус может иметь больше одного эмбеддера одновременно (например, у корпуса
типа GraphRAG отдельный эмбеддер для графовых community-эмбеддингов в Neo4j,
не совпадающий с dense-эмбеддером чанков в Qdrant). `opensearch` (BM25) своего
эмбеддера не имеет вообще — это лексический сигнал, не векторный.

На Python — то же самое одной строкой через `causa_rag_client`:

```python
embedders = client.get_corpus_embedders(realm_id="demo", corpus_id="handbook")
# ["bge_m3"]
```

Требуется и `realm_id`, и `corpus_id` вместе — `corpus_id` сам по себе не
гарантированно уникален между Realm'ами (см. `corpus_id`, который платформа
уже присылает в запросе, и `realm_id`, который присылается тем же путём —
если вы регистрировали RAG до этого поля, обновите обработку запроса, оно
уже приходит).

## Response — что должен вернуть ваш эндпоинт

```json
{
  "answer": "Текст сгенерированного ответа",
  "sources": [
    {
      "doc_id": "demo_handbook",
      "chunk_id": "demo_handbook#12",
      "structural_path": "Согласование закупки/Пороги",
      "score": 0.9123,
      "chunk_text": "Текст самого чанка, на который опирался ответ",
      "source_code": "demo_handbook",
      "article_no": "5"
    }
  ],
  "trace": {
    "stage_trace": {
      "embed_ms": 12.4,
      "dense_retrieve_ms": 45.1,
      "rerank_ms": 8.3,
      "generate_ms": 1230.5,
      "total_ms": 1296.3,
      "n_dense": 20,
      "n_sparse": 10,
      "n_merged": 15,
      "n_reranked": 5
    },
    "rendered_prompt": "первые 500 символов собранного промпта — для отладки",
    "pre_rerank_source_refs": [],
    "embedders": ["bge_m3"]
  },
  "metadata": {
    "model": "qwen3:8b",
    "request_id": "407b8318-d2f0-4196-83ff-4a44c0c4cd75"
  }
}
```

### `sources[]` — обязательные и опциональные поля

| Поле | Обязательно | Зачем |
|---|---|---|
| `doc_id` | **да** | Единственное обязательное поле — без него `recall@k`/`precision@k` не считаются вообще (платформа не выдумывает id, который вы не вернули) |
| `chunk_id` | нет (default `""`) | Гранулярность чанка, если она у вас есть |
| `chunk_text` | нет, но настоятельно рекомендуется | Без него не считаются `faithfulness`/`context_support`/`grounded_in_correct_source` — вы получите только `answer_similarity` |
| `source_code` / `article_no` | нет | Нужны, чтобы matчить golden `article_refs` датасета (структурная ссылка «кодекс/статья», а не внутренний `doc_id`) — без них `recall@k`/`precision@k` не считаются, даже если `doc_id` есть |
| `score` | нет | Чисто информативно, ни на что не влияет |

### `trace` — весь объект опционален целиком

Если вы вообще не вернёте `trace` — платформа не упадёт, просто эта запись
получит **только outcome-метрики** (сравнение текста ответа), без послойной
диагностики retrieval/rerank/generation и без диаграммы latency на странице
прогона. Верните хотя бы `stage_trace`, если можете — это дёшево (несколько
`time.perf_counter()` вокруг ваших уже существующих шагов) и сразу даёт
платформе диаграмму, где видно, какая стадия вашего пайплайна медленная.

`pre_rerank_source_refs` — список источников **до** реранкера (если он у вас
есть). Без него платформа не может отличить «retrieval не нашёл нужный
чанк» от «нашёл, но реранкер выбросил» — оба случая выглядят как нулевой
recall.

### `embedders` — сообщите платформе, каким эмбеддером вы отвечали

Список строк — какой эмбеддер (или эмбеддеры) вы использовали, чтобы ответить
на ЭТОТ конкретный запрос. Найдено вживую (тот же инцидент, что описан выше в
разделе «Как узнать, каким эмбеддером(-ами) проиндексирован корпус»): без
этого поля платформа узнаёт о несовпадении эмбеддинг-пространства только как
о жёсткой ошибке векторной БД в реальном прогоне, а не заранее.

Если вы это поле вернёте, при следующем нажатии «Проверить» на странице
Ресурсов платформа автоматически сравнит его с тем, чем реально
проиндексирован корпус (`GET /corpus/collections`), и покажет явное
предупреждение при несовпадении. **Платформа никогда не скачивает и не
пытается реализовать эмбеддер по этому значению** — сравнение чисто
информационное, только для диагностики. Если вы вообще не вернёте это поле —
не ошибка, просто мягкая подсказка вместо диагностики несовпадения.

Список, а не одна строка — если вы для одного корпуса реально используете
больше одного эмбеддера (например, отдельно для dense-поиска и отдельно для
графовых community-эмбеддингов), верните оба; если единого списка не
получается описать честно, лучше не возвращать поле вовсе, чем гадать.

## Тайм-ауты — не давайте запросу висеть бесконечно

Платформа сама ждёт ваш ответ ограниченное время (`HttpPipeline`, по
умолчанию 30с) — если вы не ответите за это время, платформа получит сетевой
`Operation timed out` без какой-либо диагностики о том, что именно у вас
зависло.

**Правило:** ваш собственный тайм-аут (на LLM-вызов, на поход в векторный
стор и т.п.) должен быть **строго меньше** тайм-аута платформы, чтобы ваш
сервис успел вернуть понятную ошибку раньше, чем платформа просто оборвёт
соединение вслепую.

Пример (взято из реальной доработки — раньше зависшая Ollama-модель вешала
запрос на 35+ секунд без единой строчки в логах):

```python
import asyncio

LLM_TIMEOUT = 25.0  # строго < тайм-аута платформы (по умолчанию 30с)

async def generate_answer(messages) -> str:
    try:
        return await asyncio.wait_for(llm_service.ainvoke(messages), timeout=LLM_TIMEOUT)
    except TimeoutError as e:
        # понятная ошибка -> FastAPI отдаст 500 с сообщением,
        # а не бесконечное ожидание на стороне платформы
        raise TimeoutError(f"LLM generation exceeded {LLM_TIMEOUT}s") from e
```

Та же логика — для похода в векторный стор/кэш/reranker, если они у вас сетевые.

## Не глотайте ошибки молча

Если у вас есть шаг, который может тихо деградировать (например, BM25/лексический
индекс строится один раз при старте из пустой на тот момент коллекции и потом
навсегда остаётся пустым) — залогируйте это явно, а лучше — сделайте
одноразовую попытку пересборки при первом реальном запросе, вместо того чтобы
процесс молча терял часть retrieval-сигнала на весь жизненный цикл:

```python
if not bm25_index.is_ready:
    log.warning("bm25_index_empty — rebuilding from vector store now")
    bm25_index.rebuild_from(vector_store.get_all_documents())
```

Ошибка должна долетать до платформы как понятный HTTP 5xx с текстом причины
— платформа сама умеет изолировать один упавший вопрос прогона и продолжить
остальные (не абортит весь прогон целиком), но только если получает **ответ**
(пусть и с ошибкой), а не зависает без ответа вовсе.

## Логи — сквозной trace_id

Прокидывайте `trace_id` из запроса в каждую строку своих логов на этот
запрос — это единственный способ найти в ваших логах, что происходило с
конкретным вопросом конкретного прогона платформы:

```python
log.info("request query=%r top_k=%s trace_id=%s", body.query[:80], body.top_k, trace_id)
# ... вся обработка ...
log.info("response n_sources=%d total_ms=%.1f trace_id=%s", len(sources), total_ms, trace_id)
```

## `GET /health` и `GET /capabilities` — опционально, но полезно

Не входят в обязательный контракт, но платформа умеет их использовать при
регистрации и для отладки:

```python
@router.get("/health")
async def health() -> dict:
    return {"status": "ok"}

@router.get("/capabilities")
async def capabilities() -> dict:
    return {
        "supports_trace": True,
        "supports_retrieval_only": True,
        "retrieve_endpoint": "/platform/retrieve",
        "supported_params": ["prompt_version"],
    }
```

## Регистрация через сырое HTTP API

Если вы не используете `causa-rag-client`, регистрация — обычный POST:

```bash
curl -X POST http://localhost:8081/external-rags \
  -H "Content-Type: application/json" \
  -d '{
    "name": "my_rag",
    "url": "http://localhost:8002/platform/query",
    "retrieve_endpoint": "http://localhost:8002/platform/retrieve",
    "supported_params": ["prompt_version"]
  }'
```

Дальше — залить golden-вопросы (`POST /datasets`) и запустить прогон
(`POST /experiments`, поле `external_rag_id` = id из ответа регистрации,
`corpus_id` — если ваш сервис мультикорпусный) через UI платформы
(«Новый прогон» → выбрать ваш RAG) либо теми же raw HTTP-вызовами.

## Регистрация корпуса, подготовленного вне платформы

Если ваш ингест пишет данные напрямую в Qdrant/OpenSearch/Neo4j — минуя
платформенную загрузку («Корпус» в UI) — корпус физически существует, но
платформа о нём не знает: не появится в списке для выбора `corpus_id`, его
эмбеддер(ы) не будет дискаверящимся через `GET /corpus/collections`. Один и
тот же публичный эндпоинт закрывает это для любого владельца — платформенной
формы или вашего собственного ингестора:

```bash
curl -X POST http://localhost:8081/corpus/collections \
  -H "Content-Type: application/json" \
  -d '{
    "realm_id": "demo",
    "corpus_id": "external_medical",
    "storage_type": "dense_only",
    "backends": {
      "qdrant": {"collection": "demo__external_medical", "embedder_id": "bge_m3"}
    },
    "owner": "external-ingestor",
    "description": "Проиндексировано собственным ингестором внешнего RAG"
  }'
```

`backends` — тот же формат, что вы видите в `GET /corpus/collections`
(см. раздел выше): один ключ на физическое хранилище, `embedder_id` внутри
каждого — там, где применимо (BM25/OpenSearch своего эмбеддера не имеет).

**Важно, чего эта регистрация НЕ делает**: сама по себе она не даёт
платформенным вкладкам Содержимое/Здоровье/Граф доступ к содержимому этого
корпуса — для этого хранилище должно быть ещё явно связано с ресурсами
Realm'а (см. `uses_realm_resources` в форме регистрации RAG). Эта регистрация
только про то, чтобы корпус был *известен*: появился в списке, стал
выбираемым `corpus_id`, его эмбеддер(ы) — дискаверящимися.

## Полный минимальный пример (FastAPI)

```python
from fastapi import APIRouter
from pydantic import BaseModel
import time
import asyncio

router = APIRouter(prefix="/platform")

class PlatformRequest(BaseModel):
    query: str
    top_k: int = 5
    filters: dict = {}
    trace_id: str | None = None
    corpus_id: str | None = None
    params: dict = {}

@router.post("/query")
async def platform_query(body: PlatformRequest):
    t0 = time.perf_counter()

    # 1. corpus_id -> правильная коллекция (см. раздел выше)
    store = resolve_collection(body.corpus_id)

    # 2. retrieval с замером времени
    t1 = time.perf_counter()
    chunks = store.search(body.query, top_k=body.top_k)
    retrieve_ms = (time.perf_counter() - t1) * 1000

    # 3. генерация, ограниченная тайм-аутом
    t2 = time.perf_counter()
    try:
        answer = await asyncio.wait_for(generate(body.query, chunks), timeout=25.0)
    except TimeoutError:
        raise  # FastAPI превратит это в 500 — платформа увидит явную ошибку
    generate_ms = (time.perf_counter() - t2) * 1000

    return {
        "answer": answer,
        "sources": [
            {"doc_id": c.doc_id, "chunk_text": c.text, "score": c.score}
            for c in chunks
        ],
        "trace": {
            "stage_trace": {
                "dense_retrieve_ms": round(retrieve_ms, 1),
                "generate_ms": round(generate_ms, 1),
                "total_ms": round((time.perf_counter() - t0) * 1000, 1),
                "n_dense": len(chunks),
            },
        },
    }
```

## Чек-лист для агента, дорабатывающего существующий RAG под этот контракт

Порядок из реальной практики хардненинга уже работающего сервиса:

1. **Тайм-ауты на все сетевые вызовы** (LLM, векторный стор, кэш) — строго
   меньше тайм-аута платформы (30с по умолчанию). Без этого один зависший
   бэкенд вешает запрос платформы на неопределённое время.
2. **`corpus_id` реально читается и маппится на коллекцию**, если сервис
   мультикорпусный — иначе прогон на "не том" корпусе выглядит как
   деградация качества, а не как баг маршрутизации.
3. **Пустой/недособранный индекс не должен быть тихим** — логировать явно и,
   по возможности, попытаться пересобрать один раз при первом запросе, а не
   оставаться сломанным на весь жизненный цикл процесса.
4. **`stage_trace` заполняется реальными числами**, а не нулями — платформа
   уже умеет рисовать диаграмму latency по стадиям, но только если получает
   данные.
5. **Ошибка = понятный 5xx с текстом причины**, не тихое зависание —
   платформа умеет изолировать один упавший вопрос прогона и не терять
   остальные результаты, но только если получает ответ.
6. **Сквозной `trace_id` в логах** — иначе воспроизвести конкретный сбойный
   вопрос из прогона платформы в своих логах почти невозможно.

## Тестирование интеграции

- Начните с малого: 1 запрос через `curl` на `/platform/query`, руками
  проверьте форму ответа.
- Затем `/platform/retrieve` отдельно — так вы отделите проблемы retrieval от
  проблем генерации до того, как гонять полноценные датасеты.
- `GET /external-rag-spec` на платформе — актуальная версия контракта, если
  что-то из этого гайда разошлось с кодом.
- Маленький датасет (5-10 вопросов) перед полным золотым набором — так
  зависание/ошибка маршрутизации видна за секунды, а не после 30-минутного
  прогона на сотнях вопросов.
